n8n · approval gate · reproducible

A stale approval cannot publish

A reviewer approves a revision. The editor then changes the text. The gate compares the content fingerprint, finds it no longer matches what was approved, and blocks publication - with no human in the loop and no way to slip the edited version through on the old approval.

The run, verbatim

{"decision":"BLOCKED","reason":"content changed after approval - approval is stale","approved_hash":"3fbd1432","current_hash":"c953f47d","alert":"slack/email alert would fire here"}

Approved fingerprint 3fbd1432. After the edit the content hashed to c953f47d. The publish branch refused.

Why it is content-hash based, not a boolean

  • 1Revision v1 is stored with a fingerprint of its exact text (FNV-1a over the content, not a timestamp).
  • 2Approval records the hash that was approved, never a bare "approved: true".
  • 3Any edit recomputes the hash. Nothing rewrites approved_hash.
  • 4An IF node compares current hash to approved hash: equal publishes, different blocks and raises the alert.
  • 5A whitespace-only edit also goes stale - which is what most teams want once they see it.

The workflow

Import this JSON into any n8n instance: webhook → revision v1 → approve → edit after approval → hash comparison → publish / block.
