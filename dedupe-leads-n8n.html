Dedupe a lead list by email in n8n — and know what the key cannot catch

Deduplication is not a node you drop in. It is one decision: what makes two rows the same person. Here is the decision, the Code node that implements it, and the real run it did on a messy export — 12 rows in, 7 usable leads out, with the other five named and explained.

The whole design is the key

Take one export from a CRM, a form tool and a spreadsheet and the same address arrives in four shapes. A dedupe that compares raw strings sees four people:

Raw value in the fileNormalised key
Marko.Petrovic@PetroCo.rsmarko.petrovic@petroco.rs
marko.petrovic@petroco.rsmarko.petrovic@petroco.rs
ana@nova.rs (trailing space from the export)ana@nova.rs
Ana Jovanovic <ana@nova.rs>ana@nova.rs

Four steps, in this order: drop a leading mailto:, take the address out of Name <addr>, remove all whitespace, lowercase. Lowercasing is safe for the domain (DNS is case-insensitive) and in practice safe for the local part on every provider that will take your money. Whitespace removal is what catches the copy-paste duplicates.

The node, in full

Code node, Run Once for All Items, mode JavaScript. It returns every input row annotated — _status is keepduplicate or rejected — so a Filter node sends the keeps to your sheet and everything else to a report. Nothing leaves the node silently.

const norm = (v) => String(v == null ? '' : v)
  .replace(/^\s*mailto:/i, '')              // mailto:ana@nova.rs
  .replace(/^[^<]*<([^>]+)>\s*$/, '$1') // Ana Jovanovic <ana@nova.rs>
  .replace(/\s+/g, '')                  // " ana@nova.rs "
  .toLowerCase();                          // Ana@Nova.RS

const EMAIL = /^[^@\s]+@[^@\s.]+\.[^@\s]{2,}$/;
const filled = (o) => Object.keys(o)
  .filter(k => !k.startsWith('_') && String(o[k] == null ? '' : o[k]).trim() !== '')
  .length;

const wrappers = items.map(i => ({ json: { ...i.json } }));
const seen = new Map();

for (const w of wrappers) {
  const row = w.json;
  const key = norm(row.email);

  if (!EMAIL.test(key)) {                  // stefan(at)dokic.rs, mila.saric@
    row._status = 'rejected';
    row._reason = key ? 'no usable email: "' + row.email + '"' : 'empty row';
    continue;
  }
  row.email = key;

  const prev = seen.get(key);
  if (!prev) {                             // first time we see this address
    row._status = 'keep'; row._reason = '';
    seen.set(key, w);
    continue;
  }

  // same address twice: keep the more complete row, fill its blanks from the other
  const [keepW, dropW] = filled(row) > filled(prev.json) ? [w, prev] : [prev, w];
  for (const k of Object.keys(dropW.json)) {
    if (k.startsWith('_')) continue;
    if (String(keepW.json[k] ?? '').trim() === '' && String(dropW.json[k] ?? '').trim() !== '')
      keepW.json[k] = dropW.json[k];
  }
  keepW.json._status = 'keep';
  keepW.json._reason = '';
  keepW.json._merged = (keepW.json._merged || 0) + 1 + (dropW.json._merged || 0);
  dropW.json._status = 'duplicate';
  dropW.json._reason = 'duplicate of ' + key;
  seen.set(key, keepW);
}

return wrappers;   // every input row comes back, annotated - nothing is dropped

Why keep the rejects at all: a row with stefan(at)dokic.rs is a real lead with a mangled address. Dropping it quietly is how a pipeline loses 10% of a list and nobody notices for a quarter. Marking it rejected with the original value quoted lets you fix the source and re-run.

What an email key cannot catch

  • One person, two addressesmarko@petroco.rs and m.petrovic@petroco.rs are two leads here. Catching them needs a second key from name + domain, and that key over-merges: every Marko at a 200-person company collapses into one row.
  • Shared inboxesinfo@ and sales@ are one address, so one lead — and often not a person you should write to at all. Filtering role addresses is a separate decision, not a dedupe one.
  • Plus addressingana+newsletter@nova.rs and ana@nova.rs are two keys. Stripping the +tag is defensible for Gmail and wrong for plenty of other providers, so this node does not do it. Decide deliberately.
  • Dots in the local partGmail ignores them, your mail server probably does not. Same trade-off, same answer: not silently.
  • Name variants with no shared address“Petrovic, Marko” with a typo'd domain stays a separate lead. That is the correct failure: a fuzzy match that merges two real customers is worse than a duplicate.

Questions this page gets

How do I remove duplicate leads in n8n?

Normalise the email to one key, keep a Map of the first row per key, merge later rows into it. The node above is the whole implementation; a Merge node set to “remove duplicates” does the same thing only when the values are already identical strings.

Why not dedupe on the full name?

Names collide across different people and split across spellings. In the sample, the three duplicates share an address but two of the three would not match by name.

Are the rejected rows thrown away?

No — they come back marked rejected with the original value quoted, so they can go to a report and be fixed at the source.

Does this send anything or call an API?

No. It reads the items it is given, writes nothing, makes no network call, needs no credential. Sending stays a separate step you build deliberately.

Will this scale to 100,000 rows?

The node is linear and holds one Map, so it runs in memory — fine for tens of thousands of rows on a normal n8n instance. Past that, dedupe in the database with a unique index, not in a workflow.

Honest limits: matching is exact after normalisation — no fuzzy name matching, no address verification, no role-address filtering. Nothing here scrapes, buys lists or sends mail.
