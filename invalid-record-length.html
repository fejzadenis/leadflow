What the message actually says

Take the numbers literally. The parser read the first line, decided the file has 7 columns, then reached a row that splits into 8 fields on the delimiter you selected. A CSV row with the wrong field count cannot be mapped onto named keys, so the node stops. The row is not corrupt and the data is not lost.

What you seeWhat it means
columns length is 7, got 8One field too many — a trailing delimiter, or an unquoted value containing the delimiter
columns length is 8, got 7One field too few — the exporter omitted the last empty cell, or a value was lost upstream
got 1The delimiter is wrong: the file is semicolon-separated and the node is set to comma, so every row is a single field
got 13 when the header has 7A field contains the delimiter and is not quoted, so one cell has been split into several

Which row is it? Twenty seconds

The number after on line is a line number in the file, counting the header as line 1. Open the CSV in a plain text editor (Notepad++, VS Code, less), switch line numbers on and look at that line and the one before it:

  • If the line ends with the delimiter (...;R; when the header has 7 fields) you have found it. This is the most common cause by a wide margin: spreadsheet exports write an empty cell after the last column and then a separator.
  • If the previous line contains a quote that is never closed, the parser is still inside that quoted field when it reaches the next line — everything after it shifts and the reported line is just where the damage finally shows.
  • If the line ends mid-address, the export wrapped a value across two lines without quoting it. Often the same character: an unquoted line break inside a field.

Why the file opens fine in Excel and still fails here

Excel is lenient by design. It accepts a trailing delimiter, pads short rows, re-guesses the separator from the first line and silently merges or splits cells when a row disagrees with the header. n8n's Extract from File node is strict: it uses the delimiter you selected and refuses a row whose field count differs from the header. So "the file is fine, I opened it" and "the node fails" are both true. The file contains rows Excel quietly repaired on screen.

Fix 2 — the two n8n settings that turn a hard stop into a diagnosis

  1. Set the delimiter explicitly. A file exported on a European Windows is usually ;, and the node defaults to ,. If the error said got 1, this is the whole problem.
  2. Turn "Skip records with errors" off while you diagnose. With it on, the node drops every affected row and reports nothing, which is how a 4,000-row import quietly becomes a 3,880-row import. Fix the rows, then leave the option off so the next bad export fails loudly instead of shrinking your list.

This behaviour, and the fact that a trailing delimiter is rejected rather than tolerated, was reported to n8n as issue #20524; the maintainers routed it as an enhancement rather than a bug, so do not wait for the node to become lenient.

Fix 3 — a Code node that pads instead of failing

When you cannot control the export (a supplier, a client, a nightly FTP drop), normalise the rows before they reach the CSV node's output. This runs once for all items and takes one item holding the file as text:

// Code node, mode: Run Once for All Items
// input: one item { csv: "<file contents as text>" }
const DELIM = ';';
const text = $input.first().json.csv.replace(/^\uFEFF/, '');
const lines = text.split(/\r?\n/).filter(l => l.trim() !== '');

const header = lines.shift().split(DELIM).map(h => h.trim() || 'unnamed');
const rows = lines.map((line, i) => {
  const cells = line.split(DELIM);
  // a trailing delimiter produces empty overflow cells - drop them
  while (cells.length > header.length && cells[cells.length - 1].trim() === '') cells.pop();
  // a short row gets the missing cells as empty strings
  while (cells.length < header.length) cells.push('');
  const out = { __source_line: i + 2 };
  header.forEach((h, j) => { out[h] = cells[j] === undefined ? '' : cells[j].trim(); });
  return { json: out };
});
return rows;

Two honest limits, because they decide whether this is enough:

  • It does not understand quoted delimiters. If a cell contains the delimiter inside quotes ("Smith, John" with a comma separator), splitting on the delimiter breaks it. That needs a real parser — which is what the node already is, and why Fix 1 exists.
  • It cannot invent a column. If two columns were merged upstream, padding produces empty cells, not recovered data. That is a repair, not a reformat.
