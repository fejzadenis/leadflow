One forwarded staffing order, parsed — before and after

The failure mode is almost never the AI step. It is what reaches the AI: a forwarded message where the useful request sits below a header block, or an HTML-only body that looks empty once you strip tags naively. Here is the logic, run on two real shapes.

Input 1 — HTML-only, forwarded

<div>---------- Forwarded message ---------<br>
From: <b>dana@northgatehotel.com</b><br><br>
We need <b>6</b> associates for <b>Saturday 15 November</b>,
start <b>6:00 AM</b> until 2:30 PM.<br>
Two must have food-handling certs.<br><br>Thanks, Dana</div>

Input 2 — plain text with a quoted reply chain

Need 3 people Monday Nov 17, 7am-3pm. Loading dock work.

--
Marco Buell
Bridgeline Events

On Thu, 13 Nov 2026 at 09:12, Chris <orders@…> wrote:

The rules that do the work

StepWhy it matters
Convert <br> and block endings to real newlines before stripping tagsOtherwise every line collapses into one, and line-anchored rules silently stop matching
Cut the quoted history at the first On … wrote: / -----Original Message-----Keeps the new request and discards three rounds of old ones
For forwarding, read after the header block, then drop From:/Date:/Subject: linesA naive "cut at Forwarded message" leaves an empty body — the exact bug that makes an AI step return nulls
Headcount needs the noun: 6 associates, not "6"Dates and times are also numbers; a bare-digit grab picks the wrong one
Accept both 15 November and Nov 17Day-first and abbreviated forms both arrive from the same client list
Normalise whitespace lastCollapsing spaces before matching destroys the multi-space patterns you rely on

What still needs a human decision: "food-handling certs" is a requirement, not a field — send it to notes and flag it, do not invent a column. And a client guessed from the sender domain must be verified against the Clients board before an order is created; an ambiguous match should raise the blocked alert, never be guessed into a real order.

What happens next in the build

  • Create the order only if the client exists on the Clients board — otherwise alert, do not create
  • Monday column values must be typed, not strings: dates as {date}, status by label, people as {personsAndTeams}
  • Hash the parsed order (client + date + shift + headcount) and check it first, so a retry never duplicates an order
